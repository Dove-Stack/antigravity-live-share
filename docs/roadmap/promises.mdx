## How voice & video work without new infrastructure

<Steps>
  1. **Signal over what exists**

      SDP offers, answers, and ICE candidates are just JSON frames — they ride
      the existing WebSocket relay exactly like `presence.cursor`.

  2. **Connect peer-to-peer**

      Each peer pair forms a WebRTC connection; audio and video never touch
      the server.

  3. **Degrade gracefully**

      No camera? Voice-only. No mic? Watch-only. The relay keeps working for
      text and presence regardless.
</Steps>

:::tip
**Every promise on this page is now shipped.** Voice, video, and access
control all ride the existing relay — no media server, no new infrastructure.
The original design promises held.
:::

## Access control, as built

<Steps>
  1. **Room tokens, not obscurity**

      `POST /rooms` now mints a share token alongside the ID. Connecting with a
      valid token grants instant entry; the first token-holder claims hostship.

  2. **Nobody reads before approval**

      Tokenless guests join as *pending*: the server relays nothing they say
      and tells them nothing except "pending". The host gets a
      `peer.request` card — approve or deny.

  3. **Read-only is a server-side role**

      The host can flip any member to read-only. The relay itself drops
      `doc.*` frames from readonly members, so trust never depends on client
      honesty. Hostship transfers automatically to an editor if the host drops.
</Steps>

## Voice chat, as built

<Steps>
  1. **Signal over what exists**

      SDP offers, answers, and ICE candidates ride the existing WebSocket relay
      as `voice.offer` / `voice.answer` / `voice.ice` frames addressed with a
      `to` field.

  2. **Connect peer-to-peer**

      A full mesh of WebRTC connections forms per session; the lexicographically
      smaller client ID initiates, so offer glare is impossible by construction.

  3. **Stream audio over data channels**

      ffmpeg pipes raw PCM from the mic; it's framed at 20ms, opus-encoded,
      sent base64 over the open data channel, decoded, and played through
      ffplay on the far side.
</Steps>

## Live video, as built

<Steps>
  1. **Same mesh, second channel**

      Each peer pair gets a `video` data channel alongside the voice one, with
      its own `video.offer` / `video.answer` / `video.ice` signaling.

  2. **MJPEG over the channel**

      ffmpeg captures the webcam at 640px/10fps and pipes an MJPEG stream;
      frames are split on JPEG markers, chunked at 16KB, and sent as JSON.

  3. **Rendered in glass**

      The receiver reassembles frames and posts them into a glassmorphism
      webview panel — one translucent tile per peer with a live indicator.
</Steps>

:::note
No camera? No mic? No FFmpeg? Signaling still works and text/presence/sync are
unaffected — voice and video degrade to a clear "unavailable" message instead
of breaking anything.
:::

## Access control, in three rules

<Accordion>
  <AccordionItem title="1. Nobody reads before approval" defaultOpen>
    Tokenless guests connect as *pending* — the server relays nothing they say
    and tells them nothing until the host approves. The gate sits server-side,
    before any content flows.
  </AccordionItem>
  <AccordionItem title="2. Read-only is a server-side role">
    The relay itself drops `doc.*` frames from read-only members, so trust
    doesn't depend on client honesty. Hostship transfers to an editor if the
    host drops.
  </AccordionItem>
  <AccordionItem title="3. Room tokens, not obscurity">
    Sessions mint a share token alongside the ID: token holders skip the gate;
    everyone else waits for the host's verdict.
  </AccordionItem>
</Accordion>
